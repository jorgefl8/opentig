¿Cómo abriría y renovaría OpenTig Dev?

Durante el desarrollo: desde el código, con npm start una vez implementado el aislamiento Dev.

Para probar el ejecutable: descomprimes un ZIP Dev y abres la aplicación. Para renovarlo, cierras solo Dev y reemplazas sus binarios. La carpeta de datos vive aparte.

Ambas formas compartirían un único perfil Dev persistente y se usarían alternativamente: cierras Dev antes de pasar de fuentes al ZIP o de cambiar de build. La estable puede seguir abierta. Abrir Dev por segunda vez enfocaría la ventana Dev existente.

La primera vez, Dev empieza con sus propios valores por defecto y sin repositorios añadidos. Lo que configures después se conserva. No copia ni sincroniza automáticamente los datos de producción.

Aislamiento confirmado: Dev debe usar siempre su carpeta de datos independiente. Si no puede resolverla o coincide con la de producción, debe detenerse con un error; nunca recurrir al perfil de producción como alternativa.
¿Puedo activar Network access en producción y Dev a la vez?

Sí: este es el comportamiento propuesto. La estable instalada y el ejecutable Dev pueden permanecer abiertos, cada uno con su servidor y su ajuste Network access independiente. Dev empieza con el acceso por red desactivado y no hereda el ajuste de producción.

Direcciones diferentes: en un equipo con IP 192.168.1.50, producción podría estar en http://192.168.1.50:6767 y Dev en http://192.168.1.50:6867. Son ejemplos: Settings y el QR muestran siempre el puerto realmente utilizado.

Proponemos rangos separados: 6767–6776 para producción y 6867–6876 para Dev. Si no hay un puerto libre, la instancia informa del error sin detener la otra. Activar o desactivar la red solo reinicia el servidor de esa instancia.

Emparejamiento independiente: emparejas el navegador con cada aplicación. Las cookies tendrán nombres distintos para evitar sobrescribirse cuando abras ambas direcciones en el mismo navegador. Cerrar sesión o revocar dispositivos en Dev no afecta a producción. La vista web de pruebas debe mostrar claramente «OpenTig Dev».

Pendiente de implementar: hoy OpenTig busca puertos libres, pero todavía no distingue estos perfiles ni sus cookies. Validaremos ambas ventanas y dos pestañas del mismo navegador, con acceso por red activo, reinicios y revocaciones independientes.

Detalle técnico: qué debemos separar para que funcione
  • Nombre e identidad de Windows, datos de Electron, cookies y bloqueo de instancia única. Configurarlos antes de abrir ventanas o sesiones.
  • Servidor y puerto: producción conserva su preferencia por 6767; Dev usaría otro rango, por ejemplo desde 6867.
  • Updater apagado en Dev y sin configuración del feed estable.
  • Atajo global Doble Control apagado inicialmente en Dev para evitar que ambas ventanas respondan.
  • Para abrir producción y Dev en el mismo navegador, proponemos cookies de sesión distintas desde el principio. Cambiar de puerto no separa las cookies. Cada servidor solo acepta y revoca sus propias sesiones.

Hoy el desktop no tiene este perfil Dev explícito. OPENTIG_HOME ya existe para la CLI, pero no configura por sí solo los datos de Electron.

Qué conservamos de la CI actual y qué falta

Ya existe: validación en Windows, pruebas de papelera en Windows/Linux y pruebas de empaquetado de CLI en Windows/Linux/macOS.

Falta: perfil Dev, artefactos descargables de prueba, publicación estable, firma y updater. La CLI actual se vuelve a empaquetar en cada sistema; el nuevo flujo transferirá el mismo archivo a los tres.

Retención propuesta: siete días para los archivos de PR y catorce para los de main. Los jobs de PR no reciben credenciales de firma ni publicación. Podemos limitar los ZIP descargables a PRs internos si queremos reducir coste.

Una comprobación fallida bloquea la publicación. Las ejecuciones obsoletas de un PR se pueden cancelar; una publicación ya iniciada debe terminar o poder reanudarse.

05 / SALIR A PRODUCCIÓN

Una versión, un commit, dos entregas.

El instalador Windows y la CLI comparten número de versión. El tag fija el código exacto que se va a publicar.

  1. 1

    Elegimos la versión

    Alineamos los números de versión y publicamos vX.Y.Z sobre el commit elegido. El flujo comprueba que coincidan.

  2. 2

    Validamos y construimos

    Las comprobaciones deben pasar antes de publicar. Se preparan dos entregas:

    Aplicación Windows x64

    Instalador NSIS firmado y archivos que necesita el actualizador.

    Servidor para navegador (CLI)

    Un único .tgz, probado en Windows, Linux y macOS con Node 24 + Git.

  3. 3

    Publicamos la CLI

    Se publica en npm el mismo tarball que pasó las pruebas. Verificamos que el registro contenga exactamente ese paquete.

  4. 4

    Hacemos visible la release completa

    GitHub ofrece el instalador, sus checksums, las notas y los metadatos de actualización. OpenTig estable ya puede detectar la versión.

Una sola línea estable permite conservar las versiones anteriores. Cada versión publicada mantiene sus archivos; la nueva pasa a ser la recomendada.
Recomendación: con qué construir y qué instalador generar

Construcción: conservar Vite y npm. Vite ya prepara la interfaz y el servidor de OpenTig. Proponemos usarlo también con entradas y salidas explícitas para main y preload, trasladando la coordinación que hoy aporta Forge a scripts pequeños. La compilación debe alimentar tanto el paquete de escritorio como la CLI sin repetir innecesariamente el build de la interfaz.

Empaquetado: electron-builder directamente. Una configuración compartida con variantes explícitas para producción y Dev, conservando recursos, módulos nativos y fuses. Una vez validado el reemplazo, retirar Forge del flujo final para mantener una sola cadena de empaquetado.

Producción: instalador NSIS completo, Windows x64, firmado y por usuario. Proponemos instalación sencilla, acceso en Inicio y actualización con electron-updater. Mantener los datos al actualizar o reinstalar y conservarlos por defecto al desinstalar.

Pruebas: ZIP Dev. Extraer y abrir, sin instalador ni actualizador de producción. Identidad, datos y carpeta de salida propios. El ensayo del instalador y del updater se hace aparte con instalaciones de prueba aisladas.

Vite+ / vp queda para una evaluación posterior. Su adopción unificaría herramientas de desarrollo, pero no es necesaria para distribuir OpenTig. En este trabajo priorizamos conservar el build actual y completar la instalación y las actualizaciones.

Esta selección de herramientas sigue siendo una recomendación; el aislamiento de datos ya está confirmado.

Por qué proponemos NSIS y qué sucede si falla la publicación

OpenTig usa ahora Squirrel.Windows. El updater propuesto, electron-updater, utiliza NSIS para este flujo de Windows. Generar un latest.yml junto al instalador Squirrel no los hace compatibles.

Corrección de esta revisión: añadir un maker NSIS a Forge no cubre por sí solo el flujo completo. Su documentación excluye actualización, firma y publicación mediante esos adaptadores. Proponemos que electron-builder se encargue del empaquetado de producción, conservando los bundles Vite donde sea viable. Primero verificaremos en Windows el servidor incluido, los módulos nativos, los recursos, los fuses y la generación de metadatos. Esa integración todavía no está probada.

Podemos preparar los assets en un draft temporal de esa versión antes de hacerla visible. Eso no es el draft rodante dev del plan antiguo.

Si npm se publica y GitHub falla, se reanuda con los artefactos originales. Si una versión ya existe con otro contenido, se detiene el proceso. No se reemplazan silenciosamente versiones estables.

Antes de la primera publicación hay que configurar la firma Windows y la publicación npm con OIDC. Si hay instalaciones Squirrel actuales, habrá que conservar sus datos en la transición.

¿Cómo usaré la CLI en Linux?

Después de publicar una versión, ejecutas npx --yes @opentig/cli@X.Y.Z serve, sustituyendo X.Y.Z por su número. El servidor muestra el enlace/código de emparejamiento para abrir la interfaz en el navegador.

La CLI sigue requiriendo Node 24 o superior y Git. Para actualizarla, paras el proceso y arrancas la nueva versión. Este plan no incorpora autoactualización del servidor.

Para probar un paquete local, usamos el archivo generado en dist/headless/, con un --home de pruebas y otro --port. No necesitamos adoptar los ejecutables autónomos por plataforma de T3.

Read more · cómo serán las notas completas

En la aplicación real, el enlace abrirá en el navegador la release exacta que se está ofreciendo. Aquí lleva a esta explicación para no confundir una maqueta con una publicación real.

El panel mostrará la versión y un resumen de sus notas. Si la release no trae notas, mostrará la versión y el enlace, sin inventar cambios. Estas notas deben prepararse como parte de la publicación.

Los enlaces serán accesibles con teclado y el panel permanecerá abierto al mover el puntero hacia ellos. Los hints usarán nuestro Tooltip, sin atributos title nativos. El contenido interactivo conservará su estilo y tendrá un manejo de foco adecuado.

Cuándo se comprueba y qué versiones puede ofrecer

Propuesta de frecuencia: una primera comprobación aproximadamente 30 segundos después del arranque y después cada cuatro horas, además de la acción manual en Settings.

Solo la distribución estable instalada tendrá el updater habilitado. Dev y los ZIP de pruebas no consultarán el feed. Si distribuimos un ZIP estable, también quedará sin updater.

El filtro debe conocer el perfil y el tipo de distribución: app.isPackaged por sí solo no distingue un ZIP de una instalación.

Descarga e instalación manuales, sin prereleases ni downgrades. Cerrar normalmente la aplicación no instalará una descarga pendiente.

Si falla la descarga, aparece otra versión o no puedes reiniciar

Comportamiento propuesto para completar los tres estados:

  • Sin novedades o sin conexión: no aparece un aviso de descarga falso. Settings muestra el resultado de la comprobación manual y permite repetirla.
  • Descarga fallida o cancelada: vuelves a poder descargar. Un clic repetido no inicia otra descarga en paralelo. El progreso al 100 % todavía debe pasar la verificación.
  • Sale otra versión mientras descargas: el progreso, las notas y «Read more» siguen refiriéndose a la versión que estás descargando. No cambiamos el destino de una descarga en curso.
  • Ediciones sin guardar u operaciones activas: se aplaza el reinicio. Puedes guardar o resolver lo pendiente y volver a solicitarlo; no se cierra el servidor mientras cancelas o decides.
  • Cierras la app sin instalar: no se instala nada automáticamente. En el siguiente arranque se vuelve a comprobar la descarga conservada antes de ofrecer el reinicio.

El control pertenece a la aplicación de escritorio. Una sesión abierta en el navegador no recibe una acción para instalar o reiniciar el ejecutable Windows.

Cómo probaremos el propio updater: dos versiones instaladas de una app de prueba y un feed local, o una VM Windows. Probar el ZIP Dev no demuestra que la instalación y actualización de producción funcionen.
07 / PARA CERRAR EL PLAN

Qué está claro y qué falta acordar

Primero fijamos el comportamiento. Después lo convertimos en tareas comprobables.

Confirmado en la conversación
  • Una sola línea pública de producción.
  • Poder probar novedades en una instancia local.
  • Datos de pruebas separados: Dev nunca escribe en el perfil de producción.
  • Icono de descarga y cambios al hacer hover.
  • Enlace «Read more» a las notas completas.
  • Tooltips con los componentes de OpenTig.
  • Seguir preparando el plan antes de implementarlo.
Propuesta técnica
  • Un único perfil Dev persistente, compartido por fuentes y ZIP.
  • ZIPs de Actions en lugar del draft dev.
  • NSIS con electron-builder para producción.
  • Publicar únicamente mediante tags estables.
  • CLI JavaScript compartiendo versión con desktop.
  • Descargar y reiniciar siempre a petición.

Decisiones para nuestra próxima conversación

  1. Uso de Dev: se propone disponer tanto de arranque desde fuentes como de ejecutable empaquetado.
  2. Ubicación del aviso: se propone junto a Settings, visible también sin repositorio abierto.
  3. Entregas públicas: se propone comenzar con instalador estable + CLI; dejar el ZIP estable como opcional.
Orden de trabajo y criterios para darlo por terminado
  1. Aislamiento Dev. Las dos aplicaciones abren simultáneamente, conservan sus propios datos y no compiten por el atajo global.
  2. Empaquetado. El instalador NSIS y el ZIP Dev arrancan con su servidor, recursos y módulos nativos correctos.
  3. CI. Los artefactos identifican su commit y la misma CLI pasa pruebas de arranque, pairing y cierre en tres sistemas.
  4. Preparación de publicación. El pipeline genera y verifica firma, tarball, instalador y metadatos en modo de validación, sin publicar. Se define la recuperación de fallos parciales.
  5. Actualización. Dos versiones instaladas de prueba permiten comprobar descarga, cancelación, errores, verificación y reinicio sin perder datos. Se prueba también aplazar el reinicio con trabajo pendiente.
  6. Primera publicación estable. Solo después del ensayo completo se publica la versión con el updater incluido. La release, el paquete npm y las notas identifican el mismo commit y versión.

La propuesta es que la primera versión pública ya pueda recibir actualizaciones: construir el pipeline de publicación no implica ejecutarlo contra producción antes de terminar el updater. README se actualizará con las funciones implementadas.

Qué cambió respecto a T3 Code y al HTML anterior

Referencia revisada: T3 Code, commit 17e34773 del 22 de septiembre de 2026. Ahora contempla stable, nightly, preview, NSIS y ejecutables de CLI por plataforma.

Tomamos como referencia el aislamiento de desarrollo y la experiencia de actualización. Para OpenTig proponemos una distribución más pequeña: una línea estable y pruebas locales.

El HTML anterior mezclaba Squirrel con electron-updater, usaba un draft rodante para main y no concretaba el perfil Dev. Este documento sustituye esos flujos por la propuesta revisada.

El código actual de T3 limita su resumen enriquecido de cambios a nightly. En OpenTig lo adaptaremos a nuestra línea estable, tal como se ha pedido.

Fuentes: workflow de T3, updater de T3, compatibilidad de electron-updater y NSIS con Forge.
